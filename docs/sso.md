# Enterprise single sign-on

Signed-in users can register an OpenID Connect client or a SAML identity provider and read the providers they administer. Adding the `sso` schema profile creates the provider catalog. Add `organization` or `organization-teams` when providers belong to organizations.

```go
ddl, err := schema.Generate("postgres", []string{"sso"})
if err != nil { return err }
store, err := sqlstore.OpenWithSchema(ctx, "postgres", databaseDSN, ddl)
if err != nil { return err }
defer store.Close()

providers, err := sso.New(sso.Options{})
if err != nil { return err }
host, err := plainauth.New(plainauth.Options{
    BaseURL: "https://accounts.example.org",
    Secret: authSecret, Store: store,
    TrustedOrigins: []string{"https://identity.example.org"},
    Plugins: []plainauth.Plugin{providers},
})
if err != nil { return err }
mux.Handle("/api/auth/", host)
```

The host imports the root `github.com/Plain-Org/plain-auth` module and its `plugins/sso`, `schema` and `adapters/sqlstore` packages. Serve these routes from an existing auth deployment that lets administrators sign in.

| Route under the auth mount | Access and behavior |
| --- | --- |
| `POST /sso/register` | Registers a provider with the account owner's direct session. An organization administrator can supply an organization ID. |
| `GET /sso/providers` | Lists the caller's personal registrations and the organization providers they currently administer. |
| `GET /sso/get-provider?providerId=company` | Returns sanitized management metadata for a single registration. |
| `POST /sso/delete-provider` | Deletes a managed registration and its attributed account links. |

```json
{
  "providerId": "company",
  "issuer": "https://identity.example.org/tenant",
  "domain": "example.org,subsidiary.example.org",
  "oidcConfig": {
    "clientId": "company-application",
    "clientSecret": "<confidential client secret>"
  }
}
```

Registration fetches the issuer's discovery document and stores the configured issuer, authorization, token and signing-key endpoints, and the UserInfo endpoint when the document advertises one. An endpoint set in `oidcConfig` takes precedence. Give the discovery origin its own exact entry in `TrustedOrigins`, return it from `TrustedOriginsForRequest` for the registration, update, sign-in and callback requests, as another runtime lets a trusted origins function do, or use the auth server's own origin. Only exact entries count, and wildcard grants apply only to browser requests and callbacks. An origin trusted this way is fetched through `Options.HTTPClient` without the public-address check. Return only origins you have vetted: never values from provider rows or registration bodies, and never a domain whose DNS a tenant controls. SAML endpoints follow `TrustedOrigins` only. Registration checks the supplied endpoints first, so a private one answers `discovery_private_host`; an untrusted discovery URL derived from the issuer then answers `discovery_untrusted_origin`, even on a private host, and for a `skipDiscovery` registration it is checked only when sign-in fetches it. Runtime discovery names an untrusted discovery origin before it checks the stored endpoints. At the callback, a private, loopback or internal token, UserInfo or key endpoint that request does not trust redirects with `error=discovery_failed` and this library's own description, where another runtime's message names the field and host. [Per-request origin tests](../adapters/sqlstore/sso_request_origins_test.go) The discovery request has a ten-second deadline and a one-megabyte response limit. Redirects and mismatched issuers fail registration, and so does any discovered URL outside an exact `TrustedOrigins` entry, so a document cannot send the client secret to another origin; another runtime also honours wildcard patterns there. This covers the revocation, end-session and introspection endpoints too, which are checked but not stored. That refusal answers `discovery_untrusted_origin` even for a private host, and its message names the field and URL, so you can add that origin as its own exact entry. Providers registered earlier are not checked again. A failed registration answers with a `code`: `discovery_not_found` (400) for a 404, `discovery_invalid_url` (400) for a malformed or non-HTTP issuer, discovery or endpoint URL, `discovery_timeout` (502) after ten seconds or a 408, `discovery_unexpected_error` (502) for any other status outside 2xx or a network failure, and `issuer_mismatch`, `discovery_incomplete`, `discovery_invalid_json`, `discovery_untrusted_origin`, `discovery_private_host` or `oidc_endpoint_redirect` (400) for an unusable document or endpoint. Any 2xx answer carries the document, and an empty one is `discovery_invalid_json`. The fetch messages are another runtime's, such as `OIDC discovery timed out: Discovery request timed out`; a network failure says `fetch failed` and never shows the transport error. `discovery_private_host` and `discovery_invalid_url` carry this library's own messages, which do not echo the URL. The document is decoded into the types OIDC Discovery defines, so a field of the wrong type answers `discovery_invalid_json`; another runtime reads the value as it is, so a numeric issuer fails its issuer check there, while a string `token_endpoint_auth_methods_supported` or a `false` `userinfo_endpoint` is accepted. The `discovery_incomplete` message lists the missing fields and the `issuer_mismatch` message names both issuers. Plain Auth also refuses URLs with credentials, a fragment or a backslash, and checks the issuer before contacting the provider. With `skipDiscovery: true` inside `oidcConfig` you can supply `authorizationEndpoint`, `tokenEndpoint` and `jwksEndpoint` directly. Any of the three you leave out is fetched from the discovery document at each sign-in, under the same trusted-origin and issuer rules, and is never stored. The discovery URL is the issuer without a trailing slash plus `/.well-known/openid-configuration`, where another runtime keeps the slash for these registrations; an unset `tokenEndpointAuthentication` then stays `client_secret_basic`. A discovery failure when sign-in starts answers with the registration codes above, and one at the callback redirects to the error callback with `error=discovery_failed` and the discovery message another runtime sends, such as `Discovery endpoint not found`, for a missing, slow, invalid or incomplete document or an issuer mismatch. [Runtime discovery tests](../adapters/sqlstore/sso_runtime_discovery_test.go) `client_secret_basic`, `client_secret_post` and `private_key_jwt` are supported. Discovery picks the first one the IdP advertises in that order, and `client_secret_basic` when it advertises none. Set `tokenEndpointAuthentication: "private_key_jwt"` and supply `Options.ResolvePrivateKey` to sign an RFC 7523 client assertion for each code exchange: the key stays in your secret store and the registration needs no client secret. The resolver runs before each token request, outside any store transaction. It receives the provider's record ID, provider ID, organization and creator, and the registrant's `privateKeyId` and issuer; bind keys to the record ID or the organization, because the registrant chooses the key ID and issuer, and a deleted provider ID can be registered again. `privateKeyId` is sent as the assertion's `kid`, and `privateKeyAlgorithm` defaults to the resolved key's algorithm, then RS256. Registration refuses an algorithm outside RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384, ES512 and EdDSA, and at sign-in an unsupported algorithm from the resolver or an older row fails the callback like a missing key, where another runtime falls back to RS256. Without the resolver, registration refuses `private_key_jwt` and sign-in answers 400. When the resolver fails or returns no key, the callback redirects with `error=invalid_provider` and `error_description=no_private_key_available` before any token request. The secret methods require `clientSecret`. [Private key tests](../adapters/sqlstore/sso_private_key_test.go) [Discovery tests](../plugins/sso/discovery_test.go)

A `providerId` must be a slug. One that names a built-in sign-in method (`credential`, `email-otp`, `magic-link`, `phone-number`, `anonymous`, `siwe`), a configured social provider or a trusted provider answers 422 in any letter case; another runtime compares exactly, but a MySQL collation folds case when accounts are looked up, so `Google` would reach `google` links.

Treat the registration response and the provider table as confidential. The successful registration response includes the submitted OIDC configuration and its client secret, with `Cache-Control: no-store`. The database stores that configuration as JSON in `ssoProvider.oidcConfig`. List and read responses expose only the masked client ID, the selected endpoints and public configuration. Domain names are normalized to ASCII and lowercase, with duplicate entries removed. Recording a domain supplies routing metadata. Management reads cover single-protocol OIDC and supported SAML registrations and report whether the current registration holds a bound DNS proof. SAML summaries also include `callbackUrl`, `idpInitiatedCallbackUrl` and, for each configured signing certificate (`idpMetadata.cert`, else `cert`), its uppercase colon-separated SHA-256 `fingerprintSha256`, `notBefore` and `notAfter` in another runtime's `Jan  2 15:04:05 2026 GMT` form and `publicKeyAlgorithm`, or `error: "Failed to parse certificate"`; certificates that only IdP metadata XML carries are not summarized, as in another runtime. All records count toward the creator quota.

### Provider fields

Declare `schema.AdditionalFields.SSOProvider` when generating the schema, and the same map in `sso.Options.ProviderAdditionalFields`. Registration and update take the fields at the top level of the body, and responses return them beside the built-in keys, as another runtime does. A missing settable `Required` field or a value of the wrong type answers 400 `VALIDATION_ERROR` in another runtime's body validation form, a `ServerOnly` one answers 400 `FIELD_NOT_ALLOWED` `<key> is not allowed to be set`, a required `ServerOnly` field without a default answers 400 `MISSING_FIELD`, and a `Hidden` field is stored but never returned. Defaults are computed before the store's transaction. The fields are not part of the provider's identity, so changing one keeps account links and the domain proof. A name or column that shadows a built-in provider key is refused when the plugin is built. Custom table and column names for the provider table are not supported. [Provider field tests](../adapters/sqlstore/sso_fields_test.go)

The default quota is ten provider records per creator across their personal and organization registrations. Set `Options.ProvidersLimit` to a pointer to a different maximum, or to zero to disable registration. Set `Options.ResolveProvidersLimit` instead to choose the quota per signed-in user, for example 10 for your administrators and 0 for everyone else; a negative number counts as reached, and an error fails the registration. It runs before the store's transaction. Organization owners and administrators can still change their providers; refuse that with `GuardProviderMutation`. [Resolved limit tests](../adapters/sqlstore/sso_limit_test.go) The live organization membership controls access on every node that shares the database, including nodes that serve only the SSO routes. Only owners and administrators can register or inspect the organization's providers. Membership and session authority are checked again before the new provider commits. An impersonated administrator cannot register a provider. Personal registrations disappear when their creator's account is deleted, and previously linked account provider IDs stay reserved. [Ownership, cleanup and concurrency tests](../adapters/sqlstore/sso_test.go)

The native Go client exposes `RegisterOIDCProvider`, `ListSSOProviders`, `GetSSOProvider` and `DeleteSSOProvider`. The registration result supplies the callback URI for IdP setup. [Compatibility tests](../conformance/sso-providers.mjs) · [SSO checklist](parity/plugins/sso.md)

## Enterprise browser sign-in

Post a trusted `callbackURL` and a `providerId`, `organizationSlug`, `domain` or `email` to `/sign-in/sso`. The response contains the authorization URL and `redirect: true`. Open that URL in the browser that started the request. A registered domain also matches its subdomains. Discovery selects eligible verified registrations first, then the most specific matching DNS suffix. A pending registration cannot shadow a proved domain. Equally specific registrations require the caller to identify the provider. An `organizationSlug` that names no organization counts as none, so the email or domain selects the provider, as in another runtime, and a request that finds no provider answers 404 `No provider found for the issuer`. Optional request fields include `newUserCallbackURL`, `errorCallbackURL`, `requestSignUp`, `scopes`, `loginHint` and `additionalParams`. A failed OIDC or SAML callback redirects to `errorCallbackURL` with `error` and `error_description`, or to the [error page](authentication.md#style-the-error-page) when the request named none, as another runtime does.

The default redirect URI ends in `/sso/callback/{providerId}`. Set `sso.Options.SharedCallback` to register `/sso/callback` for all providers. Both routes use the host's configured auth mount. The shared callback is always `{basePath}/sso/callback`; another runtime also accepts another path or a full URL, which works only when a proxy routes it to that handler. Each OIDC attempt keeps its return destinations, nonce and PKCE verifier for ten minutes, bound to the initiating browser, session and callback path. By default they are a database record that the callback consumes once. With [`OAuthStateStrategy`](social.md#keep-oauth-state-in-a-cookie) set to `OAuthStateCookie` they are sealed in the `sso_state` cookie, or the SameSite=None `saml_state` cookie for a SAML form post, and a captured copy stays valid until it expires; the identity provider's single-use code or the assertion receipt then stops a replay. Two Go nodes with the same configuration and database can handle opposite ends of a sign-in. An OIDC callback whose state cannot be used redirects to the error page with the same `state_not_found`, `state_mismatch` or `state_invalid` codes as a [social sign-in](social.md), while a provider that changed during the sign-in still sends `invalid_state` to `errorCallbackURL`. A SAML response with unusable state answers 400. [Verification hooks](hooks.md#verification-hooks) run when this record is stored and spent; a declined spend answers as unusable state and keeps the record. [Cross-instance tests](../adapters/sqlstore/sso_browser_test.go)

When Plain Auth also issues OAuth codes, your login page can pass its verified signed query as `oauth_query` on `POST /sign-in/sso`. A successful OIDC callback continues the original authorization with the new session. Your application supplies any organization picker, team picker or consent screen. Ordinary OIDC sign-in uses `newUserCallbackURL` for a new account when configured and `callbackURL` for a returning account. An identity provider denial can return to `errorCallbackURL`. SAML uses the application's `callbackURL` after a successful assertion. [Enterprise issuer login example](oauth-authorization-code.md#sign-in-through-an-enterprise-directory) · [Organization and team selection over HTTP](organizations.md#switch-organizations-and-teams-from-any-client)

Token exchange supports confidential clients using `client_secret_basic` and `client_secret_post`, and `private_key_jwt` as described above. The callback validates the ID token's signature against the provider’s JWKS, issuer, audience, authorized party, nonce and validity window. If configured, UserInfo supplies profile data using the provider-issued access token. When both sources are available they must name the same subject. Profile resolution supports the standard claims and configured email, name and image claim names, and `extraFields` for declared user fields. An error the identity provider sends to the callback comes back with its `error` and `error_description`, the description defaulting to the error; a callback without a code or error redirects with `error=invalid_request` and `error_description=authorization_code_not_found`, and one for a provider removed meanwhile with `error=invalid_provider` and `provider not found`. [Callback error tests](../adapters/sqlstore/sso_browser_test.go) A profile without a usable subject or email redirects with `error=invalid_provider` and `error_description=missing_user_info`, and a SAML one with `error=invalid_saml_response`. `mapping` names the claims for `email`, `name` and `image`; the defaults are `email`, `name` and `picture`, the subject is always `sub`, and an email claim holding a list uses its first address. `extraFields` maps user field names to claim names, and only declared fields that are not `ServerOnly` are written; a string claim fills a number or boolean field when it parses as one, and a claim with several values is not written and a warning is logged. Each mapping value must name one claim, and registration refuses other keys and shapes with 400, where another runtime accepts any `extraFields` value. `mapping.emailVerified` is accepted but ignored, because OIDC emails always start unverified. Once you declare user fields, enterprise sign-ups apply their defaults and required checks, as social sign-ups do; the values and defaults are prepared before the store's transaction. A refused field redirects to the error callback with `error` set to `MISSING_FIELD`, `VALIDATION_ERROR` or `FIELD_NOT_ALLOWED` and the reason in `error_description`, and an override to an email another user already has redirects with `error=profile_conflict`. [Claim mapping tests](../adapters/sqlstore/sso_claim_mapping_test.go) Set top-level `overrideUserInfo: true` at registration to overwrite a returning user's email, name, image and mapped user fields from the provider at each OIDC sign-in; only the top-level key counts. A changed email is stored unverified, and SAML sign-ins never override the profile. Set `Options.DefaultOverrideUserInfo` to store `overrideUserInfo` on every new OIDC registration, whatever the request says. [Profile override tests](../adapters/sqlstore/sso_profile_override_test.go) The provider ID and subject select a canonical account row. Plain Auth also checks the row’s recorded authority before issuing a session. Email addresses start unverified. A returning user needs a matching account link or the verified-domain linking conditions below. `DisableImplicitSignUp` requires `requestSignUp` before an OIDC sign-in creates an account, and a refused one redirects with `error=signup disabled`, with a space, as another runtime sends it; a refused OIDC account link likewise redirects with `error=account not linked`. `requestSignUp` applies to OIDC only: a SAML sign-in under `DisableImplicitSignUp` never creates an account and redirects with `error=signup_disabled`. A refused SAML sign-in result, `signup_disabled` or `account_not_linked`, lands on the success `callbackURL`, as another runtime sends it. For a portal response without a configured landing page it lands on the application origin, where another runtime sends it to the auth base URL. A provider that changes inside the sign-in transaction redirects with `error=SSO_PROVIDER_CHANGED` and `SSO provider changed while account linking was in progress`. [Signup tests](../adapters/sqlstore/sso_saml_defaults_test.go) The host's global signup policy and administrator bans also apply. [Released client round trips](../conformance/sso-browser.mjs)

Provider endpoints use HTTPS. Explicitly trusted loopback HTTP origins are supported for local tests. Registration and sign-in refuse only a literal private, loopback or internal host; a name that resolves to a non-public address is refused when the server connects to it, where another runtime resolves it first and answers `discovery_private_host`, so such a sign-in starts and its callback redirects with `error=invalid_grant` when the token endpoint is refused, or `error=invalid_provider` when the key or UserInfo endpoint is. For public tenant endpoints, the token, UserInfo and key requests connect directly to a validated public IP and preserve TLS hostname verification. Host-provided transports apply only to exact trusted origins. Each outbound response is limited to one megabyte. Redirects fail the exchange. [Network policy tests](../plugins/sso/identity_test.go)

The SQL adapter rechecks the provider's immutable record ID and configuration before token exchange and inside the transaction that writes the account and session. A changed issuer, tenant, endpoint or client ID cancels an in-flight authorization. Rotating only the confidential client secret preserves the provider reference. Account token storage follows the host's `EncryptOAuthTokens` setting.

An organization-bound provider adds the authenticated user as a member of the bound tenant in the session transaction. Existing roles and live invitations are preserved. A full or deleted organization cannot leave a partial identity or session. These checks also apply on sign-in nodes that share the organization database and serve only the SSO routes. Set `DisableOrganizationProvisioning` to manage membership separately. [Membership and concurrent removal tests](../adapters/sqlstore/sso_browser_test.go) The new member gets the `member` role, or `admin` with `DefaultOrganizationRole: "admin"`. Set `ResolveOrganizationRole` to choose `member` or `admin` per sign-in from the provider's user, profile, OIDC tokens and provider record. It runs before the sign-in transaction, so its user is the provider's view with no stored ID, and it runs for every sign-in through an organization-bound provider, an existing member included; another runtime runs it after storing the user and only for a new member. Another role, an error or a panic fails the sign-in with the error's API error or 500, before any account, member or session is written. [Organization role tests](../adapters/sqlstore/sso_organization_role_test.go)

With `DomainVerification` on, a social sign-in also joins an organization when the stored user's email is verified and its domain matches the DNS-proved providers of exactly one organization, as in another runtime. The role comes from `DefaultOrganizationRole` or `ResolveOrganizationRole`, whose input then carries the stored user's ID, email and name, an empty `UserInfo` and no token, and which runs only for a user who would join. Nothing happens for an existing member, a user with a pending invitation, or a domain the proved providers of several organizations serve, which logs a warning; the provider passed to the resolver is the first by provider ID in byte order, where another runtime uses locale order; `DisableOrganizationProvisioning` turns it off. The membership counts against the organization's member limit, which another runtime skips here, and a failure is logged while the sign-in stands, where another runtime fails the response. [Domain assignment tests](../adapters/sqlstore/sso_domain_org_test.go)

The native client starts the flow with `SignInSSO`. A Go flow must finish on a Go instance. The released client can use Go-created enterprise accounts on both tested implementations. Imported links require an explicit source classification before the Go runtime can use them. Arbitrary OIDC callback aliases and automatic organization assignment on ordinary signup remain open.

### Update a provider

`POST /sso/update-provider` with the manager's session changes `issuer`, `domain` or fields of `oidcConfig`; the response contains sanitized provider details. Supply `providerId` and at least one of them; other top-level fields answer 400. A missing or non-string `providerId` answers 400 `VALIDATION_ERROR` and an unknown one 404. A non-URL `issuer` answers 400 `VALIDATION_ERROR` `[body.issuer] Invalid URL`, and the issuer is stored normalized as at registration. The session is checked before the body and only the first invalid field is reported, where another runtime validates the whole body first and lists every issue. `oidcConfig` accepts the client ID and secret, the endpoints, `tokenEndpointAuthentication`, `privateKeyId`, `privateKeyAlgorithm`, `scopes`, `pkce`, `mapping` and `overrideUserInfo`, with the registration rules; a supplied `mapping` replaces the whole mapping, `skipDiscovery` is accepted and ignored, and an empty or null value answers 400. Changing the issuer, client ID or an endpoint answers 409 while accounts are linked, and changing the issuer answers 409 for OIDC and SAML alike. For a SAML directory, `samlConfig` merges `entryPoint`, `cert`, `audience`, `callbackUrl`, `idpInitiatedCallbackUrl` (null clears it), `mapping`, `wantAssertionsSigned`, `authnRequestsSigned`, `identifierFormat`, the algorithms and the `idpMetadata` and `spMetadata` fields, with the registration checks; an unknown field answers 400 `Unsupported SAML update field`, where another runtime drops it, so a misspelled policy field such as `wantAssertionSigned` is never silently ignored, and the algorithms the request names are checked again. Changing the IdP entity ID or sign-in service, the SP entity ID, NameID format, audience or signing policy answers 409 while accounts are linked; a certificate rotation does not, and the guard still sees it as a boundary change. The issuer is also the default SP entity ID and expected audience, so an issuer change moves them and a sign-in started before it fails with `invalid_state`; another runtime keeps the stored SAML issuer, and with it the SP entity ID, when the request does not also send `samlConfig`. `samlConfig` on an OIDC provider, or `oidcConfig` on a SAML directory, answers 400. A body that only replaces `samlConfig.idpMetadata.metadata` keeps the dedicated metadata path described below. The Go client exposes `UpdateSSOProvider`. `GuardProviderMutation` reviews each update, with the linked-account count and whether the identity changes, as described under [Delete a provider](#delete-a-provider), and the change is applied to the locked provider, so a concurrent secret rotation is not lost. [Provider update tests](../adapters/sqlstore/sso_update_test.go)

### Accept IdP-initiated OIDC sign-in

Set `Options.AllowIDPInitiatedOIDC` to approve reviewed registrations. A callback at `/sso/callback/{providerId}` with a code and no state then discards the code and starts a new authorization with a fresh state, nonce and PKCE verifier, which returns to the host root. The policy receives the registration's record ID, configuration reference, provider ID, issuer, client ID and organization; it runs outside any store transaction, and an error answers 503. A provider it refuses, a stateless request on the shared `/sso/callback` and a failed discovery go to the error page with `error=state_not_found`. The restarted flow cannot request sign-up when `DisableImplicitSignUp` is on. Another runtime enables this on providers defined in code and ignores `allowIdpInitiated` at registration; this library approves stored registrations by record ID and reference instead, and also ignores that key. ## Resolve enterprise users

Set `sso.Options.ResolveUser` to decide each verified enterprise identity yourself. It returns an `sso.UserResolution`:

- `ResolveContinue` signs in by the built-in rules: an existing account link, then the verified-domain email link, then sign-up.
- `ResolveLink` with `UserID` signs the identity in to that existing user, without email matching or the sign-up and trust rules. `Profile: "preserve"` keeps the user's profile; `"update"` copies the provider's name, image, email and mapped user fields to it, and a changed email takes the provider's verification. A missing user redirects to the error callback with `error=user_not_found`, and an identity another user already owns with `error=account_ownership_conflict`.
- `ResolveReject` with `Code` and an optional `Message` redirects with `error` set to the code and `error_description` to the message.

A resolver that fails, panics or returns an invalid decision, including an empty one, redirects with `error=SSO_USER_RESOLUTION_FAILED`; its error is logged without the decision. `ValidateUserInfo` still checks a link, as `link-account` the first time and `sign-in` after.

The input names the `Protocol` (`"oidc"` or `"saml"`), the `ProviderID`, and the `AccountKey`: for OIDC the ID token's issuer and subject. `User` is the normalized profile: email, its verification, name and image; mapped extra fields are not included, so read other claims from `Claims`, which holds the UserInfo claims, or the ID token claims without a UserInfo endpoint, with numbers as `json.Number`. `IDTokenClaims` is the verified ID token payload. `ProviderReference` is an opaque, transient fingerprint of the provider configuration the sign-in accepted; never store it as a tenant or user binding. Validate claims before using them for authorization. SAML sign-ins, including portal sign-ins, call the same resolver with the IdP entity ID and the signed NameID as the account key and the verified assertion attributes as `Claims`, one value as a string and several as a list; `IDTokenClaims` is nil, and a rejected portal sign-in goes to its landing page. With a resolver, every OIDC sign-in needs an ID token: a provider that returns none redirects with `error=invalid_provider` and `error_description=id_token_required_for_user_resolution`.

`ResolveUser` runs before the sign-in transaction, never inside it, so read through the store or your own database; the store then locks the chosen user and the identity and refuses a decision they no longer allow, whereas another runtime runs the resolver inside the transaction and hands it that transaction. It needs a store implementing `sso.UserResolutionStore`, as the SQL store does. To admit only active SCIM-provisioned users, see [Sign in provisioned users with SSO](scim.md#sign-in-provisioned-users-with-sso). [Resolver tests](../adapters/sqlstore/sso_resolve_user_test.go)

## Run code after an enterprise sign-in

Set `sso.Options.ProvisionUser` to run code after an enterprise sign-in creates a user and its account link, for example to create the user's record in your application. It runs after the sign-in transaction commits and after the database hooks, outside any transaction and before the session cookie is set. It receives an `sso.Provisioning` with the stored `User`, the mapped provider profile in `UserInfo` (raw claims or SAML attributes in `UserInfo.Data`), the OIDC tokens in `Token` (nil for SAML) and the `Provider`. Set `ProvisionUserOnEveryLogin` to run it on every sign-in; keep it idempotent.

```go
sso.Options{ProvisionUser: func(ctx context.Context, p sso.Provisioning) error {
	department, _ := p.UserInfo.Data["department"].(string)
	return app.UpsertProfile(ctx, p.User.ID, department)
}}
```

An `*auth.APIError` from the callback is the response, and any other error or a panic answers 500. Either way the user stays, the session the sign-in would have issued is removed, and without `ProvisionUserOnEveryLogin` the callback does not run for that user again. The store adds organization membership inside the sign-in transaction, so `ProvisionUser` runs after it; another runtime runs it before organization assignment. [Provisioning tests](../adapters/sqlstore/sso_provision_user_test.go)

## Verify directory domains with DNS

Migrate with the `sso-domain-verification` schema profile, which includes the provider catalog and adds its nullable `domainVerified` column. Enable verification on each SSO sign-in and management instance. Existing registrations can request a challenge after migration.

```go
providers, err := sso.New(sso.Options{
    DomainVerification: &sso.DomainVerificationOptions{},
})
```

1. Register the provider. The response includes `domainVerified: false` and a 24-character `domainVerificationToken`. For an existing registration, send `{"providerId":"company"}` to `POST /sso/request-domain-verification`. A 201 response returns the current token. A challenge lasts seven days. Requesting an expired challenge generates a new token. Issuing a token runs its [verification create hooks](hooks.md#verification-hooks); a declined token is returned but cannot be verified until a new one is requested.
2. Publish a TXT record at `_plain-auth-token-company` under **each** registered domain. For example, publish at `_plain-auth-token-company.example.org.` and `_plain-auth-token-company.subsidiary.example.org.` for the registration above. Its value can be the token alone or `_plain-auth-token-company=<token>`. Set `TokenPrefix` to customize the part after the underscore and before the provider ID. Use a provider ID containing letters, digits, underscores or hyphens for DNS verification. The complete label must fit within 63 characters, and each full TXT name within 253. Dotted IDs can still be managed as ordinary OIDC registrations. You can supply a private DNS resolver through `Resolver`.
3. Send the same provider ID to `POST /sso/verify-domain`. A successful response is HTTP 204 with an empty body. A missing or incorrect TXT answer returns 502. An expired or absent challenge returns 404. Repeating either operation after verification returns 409. The native client exposes `RequestSSODomainVerification` and `VerifySSODomain`. [Released client and local DNS tests](../conformance/sso-domains.mjs)

Both operations require the creator's direct session for a personal directory, or a current organization owner or administrator for an organization directory. The SQL adapter rechecks that authority and the active token after DNS lookup. It binds the proof to the registration ID, provider ID, domain list, issuer, creator, organization and OIDC configuration. Rotating just the client secret preserves the proof. A provider update that changes the domain, issuer, client ID, an endpoint, a SAML identity field or the OIDC or SAML claim mapping requires a new challenge, because the mapping chooses the email the proof vouches for; other updates carry a proven domain forward, where another runtime resets the proof only when the domain changes. Back up the related verification records with the provider catalog. A deployment importing a standalone verification flag or an externally generated challenge must request and complete a fresh challenge. Existing deployments should switch every public sign-in node to the new policy before accepting enterprise logins. [Three-engine migration and authorization tests](../adapters/sqlstore/sso_domain_test.go)

A verified domain authorizes its exact name and subdomains. Enterprise sign-in checks ownership at initiation, before contacting the identity provider on callback, and inside the transaction that creates the session. The provider can link an existing **verified local account** when the email from the authenticated identity provider is within a proved domain. An email entered into the browser cannot grant that authority. New users retain the ordinary unverified email status. Removing a TXT record after verification does not automatically revoke the stored proof. [Identity and concurrency tests](../adapters/sqlstore/sso_domain_test.go)

## Delete a provider

Send `{"providerId":"company"}` to `POST /sso/delete-provider` with a direct owner session. A personal registration belongs to its creator. Organization owners and administrators can delete registrations bound to their organization. Access follows current membership on every node. A successful response is `{"success":true}`. A repeated delete returns HTTP 404. [Client compatibility tests](../conformance/sso-providers.mjs)

The SQL adapter locks the exact registration and removes only the links whose recorded source belongs to that registration. A same-name static OAuth link is preserved. An unclassified link in the provider namespace returns HTTP 409 with `SSO_ACCOUNT_ORIGIN_REQUIRED` before anything is removed. Existing users, active sessions, organization memberships and links to other providers survive. A replacement registration receives a new internal ID. An authorization started against its predecessor cannot issue a new session through the replacement. Users whose old link was removed must establish a new authorized link before they can reuse their existing account with that provider. [Browser replacement test](../conformance/sso-browser.mjs)

Set `sso.Options.GuardProviderMutation` to apply an application deletion policy. The callback receives the locked registration ID, provider ID, organization ID, configuration fingerprint and linked-account count. Returning an error writes nothing and answers HTTP 409 with code `SSO_PROVIDER_MUTATION_REJECTED`. The callback runs outside the store's transaction on a snapshot of the locked registration, so it may read through the store or your own database, and the store commits only if it locks the same snapshot again, asking the callback again otherwise up to three times before answering 409 `SSO_PROVIDER_CHANGED`; another runtime runs it inside the transaction and hands it that transaction. Keep it free of side effects, because it can run more than once. Custom adapters can implement `sso.DeletionStore` and call the guard the same way. [SQL authorization and rollback tests](../adapters/sqlstore/sso_delete_test.go)

## Existing OAuth accounts and shared databases

A canonical account row carries a public provider ID and a subject. Two identity services can choose the same values. The SQL adapter records each new link’s source atomically with its creation, binding the canonical account ID, owner ID, subject and creation time. A managed link also belongs to one immutable registration, issuer and organization scope. Static OAuth sign-in, token access, refresh, profile lookup and provider logout require a static link. Enterprise sign-in requires the matching managed registration. A known static link and a managed link can share a public provider name when their subjects differ. Use distinct provider IDs if the issuers can produce the same subjects. [Mixed-node login and credential tests](../adapters/sqlstore/sso_browser_test.go)

Before adding an SSO schema profile to an existing deployment, inventory the OAuth accounts and confirm their original authority from the host’s provider configuration, provisioning records or identity provider. Existing static-only databases without a directory catalog can continue to use their historical static links. Mark confirmed static rows before deploying the schema to keep them available through the upgrade. When the directory catalog is present, unclassified historical links require this explicit step even if the old registration has since disappeared. [Schema upgrade test](../adapters/sqlstore/oauth_origin_test.go)

Call the trusted server-side operation for each independently verified link. Restrict access to the operator performing the migration. For a static provider supply the exact `AccountID`, `UserID`, `ProviderID` and `Subject`. For an enterprise link also supply the immutable `EnterpriseRecordID` and exact `EnterpriseIssuer`, plus `EnterpriseOrganizationID` for organization-bound registrations. Repeating the same classification is safe. Changing an established source is rejected. A newly created browser authorization or a matching email alone cannot establish the origin of an old row.

```go
err := store.ReconcileOAuthAccount(ctx, sqlstore.OAuthAccountAttribution{
    AccountID: rowID, UserID: ownerID, ProviderID: providerName, Subject: subject,
    EnterpriseRecordID: registrationID, EnterpriseIssuer: issuer,
    EnterpriseOrganizationID: organizationID,
})
```

Source records use the existing verification table and contain no provider tokens. Include them when backing up and restoring account rows. The Go SQL adapter maintains these records when linking, unlinking and deleting accounts. External writers and earlier library versions can write canonical links without recording their source and may delete all links under a shared name. Assign separate names to those writers or route link management through a source-aware deployment. [Deletion and reconciliation tests](../adapters/sqlstore/sso_delete_test.go)

## SP-initiated SAML sign-in

Enable SAML on each instance handling enterprise sign-in. Use the public HTTPS auth URL and the same SQL provider catalog, signing secret, cookie prefix and auth mount across those instances. The default SSO configuration enables OIDC. SAML uses the same `sso` schema profile. Add `sso-domain-verification` and enable DNS verification when a directory should link existing verified accounts by email.

```go
directory, err := sso.New(sso.Options{
    SAML:               &sso.SAMLOptions{},
    DomainVerification: &sso.DomainVerificationOptions{},
})
```

With an authorized administrator's cookie, send an identity provider registration to `POST /sso/register`. The native client exposes `RegisterSAMLProvider`. The top-level `issuer` is an HTTP or HTTPS URL and supplies the default service provider entity ID and expected assertion audience; another runtime also accepts other URL schemes, such as `urn:`, which answer 400 `discovery_invalid_url` here. A missing issuer, or one that does not parse as a URL, answers 400 `VALIDATION_ERROR` with another runtime's body validation message, such as `[body.issuer] Invalid URL`; the session is checked first, where another runtime validates the body before it. The issuer is stored trimmed, without the tabs and line breaks a URL parser drops. Registration accepts `samlConfig.signatureAlgorithm` and `digestAlgorithm` as URIs or short forms such as `rsa-sha256` and `sha256`, checks them against `SAMLOptions.Algorithms` and returns them with the provider. A deprecated value fails with 400 `SAML_DEPRECATED_CONFIG_ALGORITHM`, an unrecognized one with `SAML_UNKNOWN_ALGORITHM`, and one outside an allow-list with `SAML_ALGORITHM_NOT_ALLOWED`. The values are recorded only: requests are signed with RSA-SHA256. Upgrade every instance before registering providers with these fields; earlier releases cannot read them. Use `spMetadata.entityID` to give the application its own identifier. Set `idpMetadata.entityID` to the exact issuer in the IdP's signed assertions, and supply its trusted RSA signing certificate. The app accepts a PEM certificate or an array of up to eight certificates for planned overlap. A certificate list in `idpMetadata.cert` takes precedence over `samlConfig.cert`. For a manual IdP, `idpMetadata.singleSignOnService` can list the IdP's HTTPS HTTP-Redirect sign-in service, and an HTTP-POST one. The Redirect entry then replaces `entryPoint` as the AuthnRequest destination, the expected portal and ACS origin and the origin logout services must share. `entryPoint` is still required, as another runtime requires it, and both are ignored when `idpMetadata.metadata` is set. A list without an HTTP-Redirect entry, an empty list, a list with two entries for one binding, or with a non-HTTPS or query-bearing location answers 400, because this host sends AuthnRequests only by Redirect.

```json
{
  "providerId": "company",
  "issuer": "https://idp.example.org/metadata",
  "domain": "staff.example.org",
  "samlConfig": {
    "entryPoint": "https://idp.example.org/login",
    "idpMetadata": { "entityID": "https://idp.example.org/metadata" },
    "spMetadata": { "entityID": "https://accounts.example.org/saml" },
    "cert": "<PEM-encoded IdP signing certificate>",
    "wantAssertionsSigned": true
  }
}
```

The registration response retains the catalog’s OIDC-style `redirectURI` field. Use the ACS advertised by SAML metadata when configuring your identity provider. Give the IdP the public `GET /sso/saml2/sp/metadata?providerId=company` URL under the auth mount. It publishes the entity ID and exact HTTP-POST assertion consumer service (ACS) URL. To sign outgoing HTTP-Redirect requests with RSA-SHA256, set `SAMLOptions.RequestSigner` and `RequestCertificate` to the host-managed matching RSA key and certificate, then register the provider with `authnRequestsSigned: true`. Signing and verification require RSA keys of at least 2048 bits. The SQL catalog holds public IdP configuration.

Start with `POST /sign-in/sso` or the native `SignInSSO` method. Supply `providerId`, `providerType: "saml"` and a trusted `callbackURL`. A `providerType` the found provider lacks answers 400 `OIDC provider is not configured` or `SAML provider is not configured`. Each provider holds one protocol. Registering `oidcConfig` and `samlConfig` together answers 400, where another runtime stores both and lets `providerType` pick, because the OIDC subject and the SAML NameID would share the provider's account links although different authorities issue them; register two provider IDs instead. A row another runtime stored with both is not served here. A registration without `cert`, `idpMetadata.cert` or `idpMetadata.metadata` answers 400 `CERT_SOURCE_MISSING`. Open the returned URL in the initiating browser. The IdP sends a URL-encoded POST containing `SAMLResponse` and `RelayState` to `/sso/saml2/sp/acs/company`; a JSON body with the same two fields, matched by exact key, is accepted too, as another runtime accepts it. A GET to the ACS returns a signed-in browser to a trusted `RelayState`, or the application origin, and sends any other browser to the error page with `error=invalid_request`; that is the error page this library serves, `ErrorRedirectURL` or the mount's `/error`, where another runtime defaults to the application origin's `/error`. [ACS tests](../adapters/sqlstore/sso_saml_defaults_test.go) The browser must return the `Secure; HttpOnly; SameSite=None` state cookie within five minutes, the default of another runtime's `requestTTL`; set `SAMLOptions.RequestTTL` to another whole number of seconds. A later response answers 400 like other unusable state, where another runtime, whose RelayState lasts ten minutes, redirects with `error=invalid_saml_response` and `Unknown or expired request ID`. Request correlation is always on, where another runtime can turn it off with `enableInResponseToValidation: false`, because the request ID is this browser's sign-in state; use `AllowIDPInitiated` for unsolicited responses. [Request lifetime tests](../adapters/sqlstore/sso_saml_defaults_test.go) When the IdP sends an Origin header, it must match the entry point's origin. The ACS reads up to 1 MiB of form data and accepts a SAMLResponse of up to 256 KiB. Set `SAMLOptions.MaxResponseSize` in bytes for another limit up to 1 MiB. A larger response redirects to the sign-in's error callback with `error=saml_error` and an `error_description` that states the limit, like the other ACS failures, where another runtime uses the directory's fallback landing page. The limit applies after the request-body cap, so set a lower cap at the reverse proxy to refuse oversized bodies before they reach the application. It validates the signed assertion, issuer, audience, response destination, bearer recipient, request correlation and validity times. Each AudienceRestriction must name the SP entity ID or `samlConfig.audience`; otherwise the ACS redirects with `error=invalid_saml_response` and `SAML assertion audience does not match this Service Provider`. With `audience` set, one of the restrictions must name that audience, or the description is `Audience mismatch`, as another runtime sends, and an assertion without an AudienceRestriction, or whose restrictions hold only empty audiences, gets `SAML assertion is missing an AudienceRestriction`. Audience values are trimmed before they are compared. [Audience tests](../adapters/sqlstore/sso_saml_policy_test.go) Set `SAMLOptions.ClockSkew` to narrow the tolerance for assertion times; zero selects three minutes, which is also the maximum because the SAML library applies a three-minute tolerance process-wide, where another runtime defaults to five. An assertion outside its validity window redirects with `error=saml_error` and `error_description` `SAML assertion has expired` or `SAML assertion is not yet valid`. An assertion whose Conditions has neither NotBefore nor NotOnOrAfter is accepted and a warning is written to `auth.Options.Logger`, unless `SAMLOptions.RequireTimestamps` is set; then it redirects with `SAML assertion missing required timestamp conditions`. The subject confirmation's NotOnOrAfter and the issue time still bound such an assertion, and one without a Conditions element is always refused, because the SAML library requires one; it redirects with `error=invalid_saml_response` and no description, where another runtime sends `SAML assertion is missing an AudienceRestriction`. Set `SAMLOptions.Algorithms.AllowedSignatureAlgorithms` or `AllowedDigestAlgorithms` to accept only the listed URIs; list full URIs using the exported `SignatureAlgorithm` and `DigestAlgorithm` constants, since short forms such as `rsa-sha256` are accepted only in a directory's `samlConfig`. By default the ACS accepts RSA signatures with SHA-256, SHA-384 or SHA-512, and the same digests. A refused algorithm redirects with `error` set to `saml_deprecated_algorithm`, `saml_algorithm_not_allowed` or `saml_unknown_algorithm` and a description that names the algorithm only when it is one of the exported URIs. There is no warn or allow mode, where another runtime warns and accepts by default. SHA-1 signatures and digests, RSA 1.5 and Triple DES are always refused, and the allow-lists cannot include them: SHA-1 admits chosen-prefix collisions, RSA 1.5 key transport is a padding oracle and Triple DES has a 64-bit block. A signature whose method or digest the policy cannot read unambiguously, because it is missing, repeated, prefixed or in another namespace, redirects with `error=invalid_saml_response`. Digest rules also apply to each response signature's DigestMethod, where another runtime checks only the configured digest. ECDSA-signed responses are not accepted: directory certificates must be RSA, because the Go XML signature library checks ECDSA values in a form identity providers do not produce. The `SignatureAlgorithm`, `DigestAlgorithm`, `KeyEncryptionAlgorithm` and `DataEncryptionAlgorithm` constants hold the algorithm URIs. The response must carry exactly one assertion, plain or encrypted: none redirects with `error=saml_no_assertion` and a second or nested one with `error=saml_multiple_assertions`. A valid form redirects both new and returning users to `callbackURL` and issues the configured application session. A second browser cannot continue the first browser's request. A response to a request this sign-in did not send redirects with `error=invalid_saml_response` and `error_description` `Unknown or expired request ID`. The response must answer the request its RelayState started, where another runtime accepts a response to any outstanding request of the provider whatever RelayState comes with it. A response with RelayState but no InResponseTo redirects with `error=unsolicited_response` and `IdP-initiated SSO not allowed`, even with `AllowIDPInitiated`, because the RelayState binds it to this sign-in; another runtime accepts it as IdP-initiated then. A directory that changed during the sign-in redirects with `error=invalid_state` and `sso_provider_changed_during_authentication`, in OIDC as well, and a reused assertion, in either flow, with `error=replay_detected` and `SAML assertion has already been used`. Each assertion ID is recorded per IdP entity ID for 24 hours; another runtime records the ID alone until the assertion's NotOnOrAfter plus the clock skew, so a second IdP may reuse an ID here. [Response failure tests](../adapters/sqlstore/sso_saml_test.go)

`NameID` identifies the external account. Use `identifierFormat` to request a persistent NameID when your IdP offers one. It sets the NameIDPolicy of each AuthnRequest and the NameIDFormat in the SP metadata. Default attributes are `email`, `givenName`, `surname` and `displayName`; set `mapping` to select other single-valued attribute names. The name joins the first and last names, falls back to `displayName` and then to the NameID. Several values for an identity attribute refuse the response, so an ambiguous email cannot pick a mailbox; another runtime takes the first value. An email-shaped NameID supplies a missing email. `mapping.extraFields` maps user field names to attribute names; only declared fields that are not `ServerOnly` are written, when the user is created. An attribute is a string, so it fills a number or boolean field when it parses as one, and an attribute with several values is not written and a warning is logged. To accept the IdP's verification claim, set both `SAMLOptions.TrustEmailVerified` and `mapping.emailVerified`. Existing verified mailboxes still require a live matching DNS domain proof for automatic linking. Current provider configuration, organization binding and domain proof are checked in the SQL transaction that claims the assertion and creates the account or session. A SHA-256 fingerprint identifies each accepted issuer and assertion ID for replay prevention. The receipt lasts 24 hours. Avoid recording assertion forms and state cookies in proxy or request logs.

The default profile accepts a directly signed plaintext assertion over HTTP-POST. Set `wantAssertionsSigned: false` in `samlConfig` to accept an assertion covered only by its signed Response; the SP metadata then advertises `WantAssertionsSigned="false"`. An omitted value requires the assertion's own signature, where another runtime defaults to `false`, so directories registered before this release, and rows another runtime stored without the field, keep requiring it. A missing required signature redirects with `error=invalid_saml_response` and `SAML assertion signature is required`. [Assertion signature tests](../adapters/sqlstore/sso_saml_policy_test.go) This host generates the SP metadata from the directory's settings and its own keys, and serves it as `application/xml` under `Content-Security-Policy: default-src 'none'; sandbox`. `spMetadata.metadata` is refused with 400 `SAML_INVALID_SP_METADATA`, where another runtime serves the registrant's XML unchanged from the auth origin, which a browser can run script from; set `spMetadata.entityID`, `identifierFormat`, `wantAssertionsSigned` and `authnRequestsSigned` instead, which cover the policies that XML carries. `spMetadata.binding` is stored but unused, as in another runtime. The metadata route answers 404 `No provider found for the given providerId` for an unknown provider and 400 `Invalid SAML configuration` for an OIDC one. An IdP metadata document over `MaxMetadataSize` answers 400 `IdP metadata exceeds maximum allowed size (N bytes)`, before the provider checks at registration, including the quota count that another runtime makes first, and after the access check at update, as in another runtime. Private keys are refused in registrations and updates with 400, where another runtime stores `privateKey`, `spMetadata.privateKey` and `spMetadata.encPrivateKey` in the provider row and returns them. This host signs requests with `SAMLOptions.RequestSigner` and decrypts assertions with `SAMLOptions.Encryption`, so key material never passes through the HTTP API or the catalog. A directory another runtime stored with key material is not served here. Configure an IdP to use the posted HTTPS ACS and a modern SHA-256-or-stronger signature. The `additionalParams` OAuth option is unavailable for this protocol. Imported SAML links require a recorded identity authority. The historical account reconciliation interface currently supports OIDC and static social identities.

### Start single logout from the application

Set `SAMLOptions.EnableSingleLogout` on the instances serving the provider. Supply the host’s matching RSA `RequestSigner` and `RequestCertificate`. Logout messages from the IdP must be signed. Another runtime accepts unsigned ones unless `wantLogoutRequestSigned` and `wantLogoutResponseSigned` are set, which would let any site end a user's sessions. Both logout routes are mounted whenever SAML is configured, as another runtime mounts them, and answer 400 `SINGLE_LOGOUT_NOT_ENABLED` while single logout is off; the start route checks the browser session first. Starting a logout, or an IdP logout request, for an unknown provider answers 404 `SAML_PROVIDER_NOT_FOUND`; a logout response without this browser's logout cookie is refused as invalid before any provider lookup, and for a directory without an IdP logout service 400 `IDP_SLO_NOT_SUPPORTED`. [Logout code tests](../adapters/sqlstore/sso_saml_defaults_test.go) An IdP directory can specify a HTTP-Redirect logout service in its imported metadata XML or register it explicitly.

```json
{
  "singleLogoutService": [
    {
      "Binding": "urn:oasis:names:tc:SAML:2.0:bindings:HTTP-Redirect",
      "Location": "https://identity.example.org/logout"
    }
  ]
}
```

Put this object’s `singleLogoutService` field under `samlConfig.idpMetadata`. The supported IdP logout endpoint uses HTTPS, shares the configured sign-in origin, and has no preset query or fragment. The SP metadata publishes the service’s Redirect SLO URL and the request-signing certificate for eligible directories. Enabling logout alone leaves the existing AuthnRequest signing policy in effect.

After logging in with SAML, send `POST /sso/saml2/logout/{providerId}` with the active browser cookie and an optional trusted `callbackURL`; without one the browser returns to the auth base URL, as in another runtime. The native SDK’s `StartSAMLLogout(ctx, providerID, callbackURL)` returns a URL for the same browser to open. The signed IdP assertion must have supplied exactly one authentication statement with a nonempty SessionIndex. The Go service requires a record from that login and the same directory configuration. A password session or a SAML login predating this setting can use ordinary application sign-out.

The start transaction revokes the selected local session and records a single-use return before issuing its HTTP 302. Other logins for the same user stay active. The IdP receives the original NameID, qualifiers and SessionIndex in a signed Redirect LogoutRequest. Its successful HTTP-Redirect response must include the original request ID, the exact issuer and HTTPS destination, the opaque RelayState and a query signature using RSA-SHA256, RSA-SHA384 or RSA-SHA512. The browser returns a dedicated Secure, HttpOnly, SameSite=Lax cookie. Set `SAMLOptions.LogoutRequestTTL` to a positive whole number of seconds to change the five-minute default.

The auth host consumes the pending response once and redirects to the previously stored callback. A timeout or failed IdP response leaves the local session revoked. If the browser signed in again during the round trip, the acknowledgement preserves the newer session. A short-lived verification row holds the external NameID and SessionIndex through the local session expiry. SQL session renewal extends the binding in the same transaction. A second row holds the return destination and browser-binding digest through the logout deadline. Neither row needs a reusable session token. Avoid logging the signed Redirect query, which carries protocol identifiers. With [verification hooks](hooks.md#verification-hooks), the binding runs them when the sign-in stores it, when renewal extends it, and when either logout direction removes it; the pending return runs them when logout starts and when the response spends it. A declined binding signs in without single logout. A declined return still signs the browser out and sends it to the IdP, but its response is refused.

### Accept a logout request from the identity provider

Set both `SAMLOptions.EnableSingleLogout` and `SAMLOptions.EnableIDPInitiatedLogout` on the instances serving the SLO URL. The IdP can send a signed HTTP-Redirect `LogoutRequest` to `GET /sso/saml2/sp/slo/{providerId}` without an application cookie. Logout uses HTTP-Redirect only, the binding the SP metadata advertises, where another runtime also accepts HTTP-POST as a form or JSON; accepting a cross-site POST would need the SLO path exempt from the cross-site check and a `SameSite=None` logout cookie. A request with neither a non-empty `SAMLRequest` nor `SAMLResponse` redirects to a trusted `RelayState`, or the application origin, with `error=invalid_request` and `error_description=missing_logout_data`, before any provider lookup. The host checks the query signature, registered issuer, exact HTTPS destination, issue time and any `NotOnOrAfter` deadline. Accepted request algorithms are RSA-SHA256, RSA-SHA384 and RSA-SHA512. Supply the original plaintext NameID, including its format and qualifiers, and exactly one SessionIndex. The optional signed RelayState carries up to 80 bytes of opaque IdP state.

The database revokes every recorded local session that matches the current immutable directory registration, its configuration, the complete NameID and the SessionIndex. A matching browser cookie clears on that response. With the optional session-cookie cache enabled, another browser can display its old session view until the cache expires. Protected operations verify revocation in storage. Password logins, other IdP sessions and another directory’s records stay active, including when two directories use the same IdP certificate and subject. A directory enrolled in DNS verification must still have its matching proof. A configuration change or directory recreation requires a fresh SAML login to create a binding under its new authority.

The service returns an RSA-SHA256 signed LogoutResponse to the registered IdP endpoint, with the request ID in `InResponseTo` and the original RelayState. Imported XML may specify a separate HTTPS `ResponseLocation` on the same IdP origin. A valid request with no matching sessions receives the same success response. The shared database records the request ID once per registration and issuer for 24 hours. Replaying it returns HTTP 400 and preserves any later login. A binding a verification hook keeps stays stored, unable to end any session; its session still ends. Request and response are browser redirects. The service never fetches the IdP logout endpoint.

Run the current SQL adapter on every session-renewing instance to carry the logout binding through sliding renewal. Sessions whose bindings expired on an earlier writer need a fresh SAML sign-in. Enable single logout when issuing the original login. Both logout directions require its recorded NameID and SessionIndex. SOAP logout, omitted or multiple SessionIndexes, BaseID and encrypted logout identifiers remain open.

### Sign in from a reviewed IdP portal

An IdP portal can send a signed assertion directly to its registered HTTP-POST ACS. Use this flow when users select the application in their identity provider. The default configuration requires a browser-bound service-provider request. To enable portal login, give each instance a host-owned policy that authorizes the specific directory. The service supplies the immutable registration ID, current configuration reference, provider name, actual assertion issuer, effective IdP entry point and organization ID.

```go
portal := &sso.SAMLOptions{
    IDPInitiatedCallbackURL: "/employee",
    AllowIDPInitiated: func(ctx context.Context, d sso.SAMLDirectory) (bool, error) {
        return d.RecordID == approvedRegistrationID &&
            d.Reference == approvedConfigurationReference &&
            d.OrganizationID == companyOrganizationID &&
            d.Issuer == "https://identity.example.org/metadata" &&
            d.EntryPoint == "https://identity.example.org/sso", nil
    },
}
enterprise, err := sso.New(sso.Options{SAML: portal})
```

Obtain the registration ID from the administrator’s successful registration response. Source the policy from trusted host configuration and apply it on all replicas serving the callback. Registration names can be reused after deletion. Pinning the immutable record prevents an old approval from following its name to a new directory. Use the trusted store’s `FindBrowserProvider` method with the provider name and protocol `saml` to obtain the current reference after reviewing the signing certificates. Pinning that reference requires a fresh approval after a catalog change, including signing certificate rotation. A policy error fails the request with HTTP 503.

Configure the IdP to submit a top-level form containing `SAMLResponse` directly to the HTTPS ACS. Omit `RelayState` and `InResponseTo` from an unsolicited response and its subject confirmation. The browser must send an `Origin` matching the configured IdP entry point exactly, including any nondefault port. Choose an IdP origin whose pages the organization trusts to initiate sign-in. When supplied by the browser, `Sec-Fetch-Dest` must be `document`. Some IdPs use a different frontend origin or suppress Origin through referrer policy. Those deployments can use the browser-bound SP flow. Submitting an invalid RelayState never starts portal login.

Use `samlConfig.idpInitiatedCallbackUrl` for a directory landing page. For portal requests the server tries that URL, the host’s `SAMLOptions.IDPInitiatedCallbackURL`, and then the directory’s `samlConfig.callbackUrl`. It skips untrusted destinations and the auth host’s own ACS path, and falls back to the application origin. [Directory landing test](../adapters/sqlstore/sso_saml_mapping_test.go) `DisableImplicitSignUp` permits returning accounts and rejects first-time portal signup. The ACS validates signed subject, issuer, recipient, audience, time bounds and optional directory encryption. The SQL transaction checks current authority and DNS requirements and consumes the assertion once across replicas. A replay redirects with `error=replay_detected`, and a portal response the host does not allow with `error=unsolicited_response` and `IdP-initiated SSO not allowed`. The Go host’s directory approval and mandatory browser Origin are additional requirements for this mode.

### Encrypt assertions for a directory

Configure the same RSA recipient key and its X.509 certificate on each instance serving that directory. Load them through the host’s secret manager or protected files. The key must be at least 2048 bits. The following helper loads PEM files and returns the setting for `SAMLOptions.Encryption`.

```go
func assertionRecipient(certFile, keyFile string) (*sso.SAMLEncryption, error) {
    pair, err := tls.LoadX509KeyPair(certFile, keyFile)
    if err != nil {
        return nil, err
    }
    key, ok := pair.PrivateKey.(*rsa.PrivateKey)
    if !ok {
        return nil, errors.New("SAML assertion recipient requires an RSA key")
    }
    cert, err := x509.ParseCertificate(pair.Certificate[0])
    if err != nil {
        return nil, err
    }
    return &sso.SAMLEncryption{PrivateKey: key, Certificate: cert}, nil
}
```

Set `samlConfig.idpMetadata.isAssertionEncrypted` to `true` when registering the directory. The Go service also accepts `samlConfig.spMetadata.isAssertionEncrypted` as a requirement for incoming assertions. When either flag is true, a host with no recipient key rejects that registration. The SQL catalog stores the directory’s public settings. Supply only public settings in HTTP registrations; private keys answer 400.

Give the IdP this directory’s SP metadata. Its encryption key descriptor advertises the public recipient certificate, AES-256-GCM and XML Encryption 1.1 RSA-OAEP with SHA-256 and MGF1-SHA256. An assertion may wrap its key with RSA-OAEP, `rsa-oaep-mgf1p` with a SHA-1 or SHA-256 digest or XML Encryption 1.1 `rsa-oaep` with a SHA-1, SHA-256, SHA-384 or SHA-512 digest and MGF1; a missing digest means SHA-1, the XML Encryption default, and other OAEP parameters are refused. It may encrypt with AES-128, AES-192 or AES-256 in GCM or CBC mode. AES-CBC is accepted only inside a Response the IdP signed, and only the signed ciphertext is decrypted, which another runtime does not require, because an unsigned CBC ciphertext is open to a padding-oracle attack; without that signature the ACS redirects with `error=invalid_saml_response` and `SAML response must be signed when the assertion is encrypted with AES-CBC`. Set `SAMLOptions.Algorithms.AllowedKeyEncryptionAlgorithms` or `AllowedDataEncryptionAlgorithms` to accept only the listed URIs; the SP metadata then advertises them in that order, data ciphers first, and another algorithm redirects with `error=saml_algorithm_not_allowed`, naming the key transport first. An empty list accepts every supported algorithm, where another runtime treats any list it is given as an allow-list. An assertion whose key is wrapped with RSA 1.5, whatever the content cipher, or encrypted with Triple DES redirects with `error=saml_deprecated_algorithm`, naming the key transport first; any other algorithm outside this profile redirects with `error=invalid_saml_response`. [Encryption profile tests](../adapters/sqlstore/sso_saml_policy_test.go) The signature algorithm policy also applies to the decrypted assertion. Configure the IdP to sign the assertion, then encrypt the entire signed assertion. The content and wrapped key must each use an inline `CipherValue`. The IdP may additionally sign the outer response. The ACS checks the recovered assertion’s signature, claims, browser state, directory authority and issuer-bound replay receipt. A signed outer response with an unsigned assertion is rejected unless the directory sets `wantAssertionsSigned: false`.

One recipient key is active per host. Coordinate recipient-key changes across instances and the IdP, and start a fresh login after the switch. Each host accepts requests encrypted for its active key. The separate request-signing key and the IdP’s verification certificates can be managed independently. Encrypted NameID or attribute fields, detached encrypted keys and multiple simultaneous recipient keys remain open.

### Import and rotate IdP metadata

An authorized directory manager can submit the IdP’s metadata XML directly in `samlConfig.idpMetadata.metadata` on registration. Obtain it over a trusted channel and verify the issuer and signing certificates with the IdP administrator. Include the top-level `issuer`, `domain`, `providerId` and `samlConfig.entryPoint` from the registration example. The XML supplies the effective IdP entity ID, redirect endpoint and signing certificates. A URL string is rejected. The service parses the submitted bytes locally.

Use one SAML 2.0 `EntityDescriptor` containing one `IDPSSODescriptor`, one HTTPS HTTP-Redirect SSO service, and up to eight signing keys. For each signing key, use a separate `KeyDescriptor` with one X.509 certificate and a 2048-bit or larger RSA public key. Signing and unspecified key usage are accepted. Encryption-only keys cannot authorize a login. Where the IdP requires signed requests, configure the host’s request signer and certificate. Entity and role expiry apply to the resulting authority. The default XML limit is 100 KiB. Set `SAMLOptions.MaxMetadataSize` in bytes for another limit within the 1 MiB request-body cap. MySQL’s canonical TEXT column also limits the complete serialized provider configuration to 65,535 bytes. Federation aggregates, remote metadata retrieval, periodic refresh and metadata-signature trust anchors remain open.

Use `POST /sso/update-provider` with the same manager session to replace the XML. The Go client exposes `UpdateSAMLMetadata(ctx, providerID, xml)`. The response contains sanitized directory details.

```json
{
  "providerId": "company",
  "samlConfig": {
    "idpMetadata": { "metadata": "<md:EntityDescriptor …>…</md:EntityDescriptor>" }
  }
}
```

For a rotation, publish an overlapping document containing the current and next certificates. Switch signing keys at the IdP, verify a new login, then replace the document with the next certificate alone. Each replacement invalidates sign-ins started under the prior configuration. Existing account links and an established DNS proof survive a signing-key rotation. The update holds a database lock, checks the live direct session and organization role, and rejects an issuer or SSO-service change with HTTP 409 while accounts are linked. A change of identity on an unused directory requires a new DNS proof when verification is enabled. The optional `GuardProviderMutation` receives the linked account count and the authentication-boundary change flag before the update commits. This endpoint currently accepts only replacement of the inline IdP metadata.
